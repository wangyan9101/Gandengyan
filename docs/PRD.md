## 1. 产品定位、目标与边界

面向熟人朋友组局的休闲干瞪眼微信小游戏。最终支持2～8名真实玩家同房实时对战，重点验证6人体验；保留本地真人＋AI模式用于练习和规则验证。

最终用户可通过微信小游戏体验码或分享入口启动，无需安装独立App。房主配置房间，玩家加入、准备、对局、结算并再来一局。规则由服务端复用现有 `packages/rules` 唯一裁决，私人手牌隔离，断线可恢复，积分不可重复结算。

仅使用**不可兑现的娱乐积分**，不与财物挂钩。禁止真实货币下注、输赢转账、充值、提现、兑换、现金奖池、抽成、交易撮合或支付接口。

### 1.1 首个可交付微信版本的成功标准（目标，尚未达成）

1. 房主与至少5位获授权的体验成员在微信内扫码或通过邀请进入同一房间。
2. 六人完成一整局真实联机对局，并在同房连续再开一局。
3. 对手无法获取未公开的手牌和隐藏牌堆顺序；非法操作不改变权威状态。
4. 断线后重新认证，恢复本人席位、手牌与最新公共状态。
5. 实测覆盖1/2副牌、2/6/8人场景，既有单机模式持续通过回归。
6. 微信开发者工具及常见安卓/iOS真机各至少一款完成启动、触摸和前后台切换验收。
7. 体验版资格和体验成员在微信后台核验；正式公开发布另行核验主体、棋牌类目、资质、备案、隐私与审核条件。体验版不视为正式上线，不预设个人主体必定获批。

## 3. 用户角色与流程

角色包括房主、普通玩家、体验成员/正式玩家，以及后续云端运营维护者。

### 3.1 当前本地模式

- 单机：主界面配置 → 创建本地游戏 → 真人与AI按轮操作 → 结算或规则暂停 → 重开/返回。真人固定第一席并任庄家；返回主界面放弃本地局且不记分。
- 本地联机大厅：选择本地联机 → 连接服务端并取得临时访客身份 → 房主配置并建房 → 其他连接输入房号加入 → 全员在线且准备、人数满员 → 房主开始 → 服务端发牌并进入真实对局 → 统一结算 → 全员重新准备，由房主开下一局，上局赢家任庄。

### 3.2 最终微信联机流程（规划）

打开小游戏 → 在微信授权范围内取得可信身份 → 选择单机或联机 → 房主创建并配置房间 → 分享邀请/房号加入 → 服务端核验成员与席位 → 全员准备 → 服务端洗牌发牌 → 出牌/过牌与补牌 → 首位出完结算 → 查看积分 → 同房再来一局。

重连时重新认证并核验席位，从服务端取得同一版本的公开与本人私有快照；不能依赖客户端缓存恢复权威牌局。

异常流程覆盖房满、房间不存在/解散、无体验资格、网络中断、切后台、邀请过期、非法牌型、过期版本、重复请求、中途退出与 `awaiting-rule`。错误必须明确反馈，不能静默卡死。

### 4.2 牌局规则与积分约束

- 使用已记录的 `gdy-default-v1` 规则版本；默认项不能宣传为全国统一玩法，细节与未决项见 [RULES.md](RULES.md)。
- 庄家初始6张，其他玩家各5张；其余牌为共享但隐藏的未发牌堆，不代表牌序公开。
- 大小王只能搭至少一张普通牌作癞子，不可单出、不可纯王组牌，不增设王炸。
- 普通接牌、炸弹比较与癞子解释由现有引擎裁决。连续其他玩家全部过牌后，从最后出牌者起按座位顺序每人最多补1张，余牌不足按序分到耗尽。
- 首个出完全部实体手牌者立即获胜。每个输家扣 `min(剩余实体牌数 × 2^B, cap)`，赢家收入为实际扣分总和；制胜炸弹计倍，王按实体牌计1张。
- 例：输家分别剩3/7张，B=2、cap=20，结果为赢家+32、输家−12/−20，总和0；赢家收入可超过20。
- 每张实体牌始终唯一且守恒。非法动作不改变输入状态、倍率或版本；相同输入产生相同结果，配置冻结。
- 仅剩王且需自由领出时进入 `awaiting-rule`，先按现有流程补牌，仍不能领出则暂停、不判胜、不扣分。正式联机对局发布前须定稿，不能由网络层擅自判胜/判负。
- 规则引擎单局结束后拒绝新动作；当前服务端内存账本以roundId唯一去重，状态、回执与记账在同步处理内提交；持久化事务仍待后续实现。

## 5. 技术架构与云端策略

### 5.1 单仓库与模块边界

```text
Gandengyan/
├── assets/                  # 现有Cocos界面、场景、脚本及.meta
├── packages/rules/          # 纯规则，客户端和后续服务端共用
├── packages/local/          # 保留本地AI会话
├── packages/session/        # 通用会话、本人提示与牌型解释
├── packages/protocol/       # 类型化消息、运行时验证与公开/本人DTO
├── packages/remote/         # NetworkClient、房间客户端及远程会话适配
├── server/                  # 已实现本地Node.js + TypeScript + WebSocket房间服务
├── tests/                   # 离线规则/应用测试与独立网络集成测试
└── docs/                    # 需求、规则、架构、协议、验收及后续部署文档
```

依赖方向为表现层→应用/会话接口，本地适配器→规则引擎，远程适配器→协议/传输，服务端→规则/协议/持久化接口。规则不得依赖Cocos、微信、CloudBase、DOM、Node或IO；时间与随机不得在确定性动作函数中读取。客户端镜像只同步白名单共享包，不包含Node服务端依赖。

### 5.2 实施顺序与云端候选

当前以已授权的本地Node.js + WebSocket路线推进，先保留单机、完成本地联机基础与房间，再按单独授权实现真实对局及恢复。现阶段不启用、购买或部署腾讯云资源。

原V1.0提出优先评估CloudBase云函数＋文档型数据库＋受控实时状态更新，并在监听、延迟或事务不足时考虑云托管/独立WebSocket。该建议保留为**云阶段候选方案**，不是已选SDK或已实现能力；原建议中的 `cloud/functions/` 不在本轮创建，`server/` 也不再被描述为尚不存在的可选目录。

云阶段须另行确认方案、费用、免费额度期限、认证、小游戏SDK兼容性、事务能力、安全规则、实时延迟和后台恢复；不承诺永久免费或无限房间。先做6人少量测试，再扩展8人及多房间，开发/测试/生产环境分离。

### 5.3 安全、一致性与隐私

- 服务端是唯一可信状态源，核验身份、成员、房主、席位、牌归属、房间/牌局阶段、配置及版本；客户端不得直接写手牌、牌堆、倍率、回合或结算。
- 本地大厅身份为服务端分配并绑定连接的临时访客，不等于微信身份；后续服务端验证真实账号，不信任请求内playerId。
- 请求包含协议版本、requestId、roomId、roundId、expectedVersion，外部输入使用unknown及运行时白名单校验，并设置长度、频率与连接限额。
- 房间版本与牌局版本分开；同房动作串行化或事务/条件更新，拒绝陈旧写入。去重键包含认证身份、房间、局与请求ID；同ID不同载荷拒绝。
- PublicRoomView/PublicGameView只包含必要公开信息；SelfGameView只含本人手牌。成员公开信息不等于互联网匿名可读，不广播完整GameState、其他人的手牌、隐藏牌序或随机源。
- 快照恢复以服务端为准，客户端丢弃旧版本，版本空洞/重连后重新拉取授权快照。
- 数据库默认拒绝；权威文档、去重及账本禁止客户端访问，不依赖客户端过滤或TypeScript字段类型保证保密。
- 积分采用整数，结算幂等且可审计；跨资源通知在持久化方案确定后验证事务发件箱及补发机制。
- 分享参数只携带可过期邀请，不含手牌、凭证或云密钥；服务端重新核验加入资格和空席。
- 日志关联requestId/roomId/roundId/版本/错误类别，不记录私有手牌、令牌或生产身份调试数据。不提交AppSecret、Token和云凭证，秘密只保存在受控服务环境。

## 6. 非功能要求与验证

- 正确性：原有322项测试持续通过；新增规则覆盖确认正反例、输入边界和不变量，断言可观察行为。配置版本、确定性、实体牌守恒与非法命令不变均需验证。
- 可靠性目标：短暂断网、切后台后恢复原局；当前已实现同客户端内存凭证恢复，切后台与微信真机还需实测。超时仅提示、不托管/判负已获确认。
- 安全验证：身份伪造、跨房间访问、私有投影、重复结算、并发出牌、乱序、重试和重连；单机进程内隔离不等于线上安全。
- 性能：以2/6/8人实测延迟、同步成功率、云资源消耗作为后续上线依据；具体阈值待本地/云端POC后确认。
- 资源与可维护性：固定开发工具及依赖版本、提交lockfile，避免大规模工具链；保持现有工程身份和模块单向依赖。
- 当前命令：`npm run check`验证规则/应用/服务端类型、离线测试与镜像；`npm run check:all`额外检查客户端（需Creator生成类型声明）；`npm run check:network`单独执行真实回环网络测试。
- Creator浏览器预览、目标构建、微信开发者工具和安卓/iOS真机分别验收；Node测试不能报告成端上通过。
